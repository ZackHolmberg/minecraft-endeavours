# v2 research: Minecraft LLM-agent SOTA and mineflayer tooling

Date: 2026-10-09. Sources: arXiv/GitHub/npm registry checked today. Items marked (unverified) were not confirmed from primary text.

## 1. Voyager (Wang et al. 2023) https://arxiv.org/abs/2305.16291
- Mechanisms: (a) automatic curriculum (GPT-4 proposes next task from state + progress), (b) skill library = verified JS code programs indexed by embedding of GPT-3.5-generated description, retrieved top-5 by task+env feedback, (c) iterative prompting: env feedback + execution errors + self-verification critic (max 4 rounds per task before abandoning).
- Actions are LLM-written mineflayer JS (code-as-policy) using a small set of control primitives (mineBlock, craftItem, smeltItem, placeItem, killMob, exploreUntil...).
- Results (Table 1): iterations to wooden/stone/iron/diamond tool: Voyager 6/11/21/102(1 of 3 runs) vs AutoGPT 92/94/135/fail; ReAct, Reflexion never got past wood. 63 unique items (3.3x), 2.3x distance. Zero-shot new world: diamond pickaxe 19, golden sword 18, lava bucket 21, compass 18 iterations (4/4 vs 0/4).
- Ablations: removing self-verification -73% items (most important); no curriculum -93%; GPT-3.5 instead of GPT-4 code gen -5.7x. GPT-4 is ~15x GPT-3.5 cost (2023).
- Cost: very high - many GPT-4 calls per iteration (curriculum + action + critic + up to 4 retries), long code outputs. Authors cite cost as top limitation.
- Reported failures: hallucinated items ("copper sword"), calls to nonexistent APIs, gets stuck, verifier misjudges.
- Transfer: see synthesis. Key: verification + persisted skills + curriculum ordering; NOT code-gen-per-task.

## 2. Mindcraft + MineCollab (kolbytn/mindcraft) https://github.com/kolbytn/mindcraft ; https://arxiv.org/abs/2504.17950 ; https://mindcraft-minecollab.github.io/
- Mechanisms: mineflayer bot; LLM emits "!command(args)" calls from ~47 high-level actions (!craftItem, !goToPlayer, !searchForBlock, !placeHere, !givePlayer...); observation via query commands (!inventory, !nearbyBlocks, !stats) to keep context small; RAG of few-shot examples via embeddings; optional "coding mode" (LLM writes JS; disabled by default, needs allow_insecure_coding, security warning); "modes" = LLM-free reflexes (self_preservation, unstuck, cowardice, item_collecting, torch_placing, hunting, elbow_room) that interrupt the agent; self-prompter for autonomous goals; JSON task files (goal, initial inventory, target items, timeout).
- Active: 5.8k stars, commits through Oct 2026, supports MC up to 1.21.11 (1.21.6 recommended), Node 18/20 (24+ native-dep issues). 16+ providers incl. Claude.
- MineCollab benchmark (cooking / crafting / construction, 2-5 agents): binary success for cook/craft, edit-distance for construction. Scores (Sonnet 3.5 / GPT-4o / Llama3.3-70B): crafting 0.47/0.17/0.16, cooking 0.64/0.40/0.36, construction 0.36/0.31/0.19. SFT'd Llama-8B on successful trajectories: +17% cooking, matches 70B on construction. Perf falls ~90% (2 agents) -> <30% (5 agents) in cooking; -15% when detailed plans must be communicated. Construction: <40% blocks right even for best model.
- Failure modes: undoing own work (place/destroy loops), coordination on shared resources, failing to execute communicated plans, multi-step instruction misreads.
- Token profile: command-based (short outputs), observation-on-demand; no hard per-task numbers published.
- Transfer: modes/reflexes layer (we have auto-behaviors); queryable state commands vs always-injected context (we inject; keep it compact); task JSON format (goal + starting inventory + target + timeout) is a good eval harness model; construction needs blueprint -> deterministic builder, not LLM block-by-block.

## 3. GITM - Ghost in the Minecraft (Zhu et al. 2023) https://arxiv.org/abs/2305.17144 ; https://github.com/OpenGVLab/GITM
- Mechanisms: (1) LLM Decomposer: goal -> sub-goal TREE using wiki/recipe knowledge, goal format (Object, Count, Material, Tool, Info); (2) LLM Planner: sub-goal -> action list over only NINE structured actions (equip, explore, approach, mine/attack, dig_down, go_up, build, craft/smelt, apply) with feedback loop for replanning; (3) LLM Interface: hand-written scripts execute structured actions from observations; (4) text memory: successful action sequences stored per sub-goal; after 5 successes, LLM summarises into a "reference plan" reused for that goal.
- Results: ObtainDiamond 67.5% (prev SOTA ~20%, +47.5pp); first agent to obtain all 262 Overworld tech-tree items; no GPU, single 32-core CPU node, ~2 days for training-free setup (vs thousands of GPU-days for RL).
- Ablation: decomposition, feedback, external knowledge and memory each materially raise intermediate milestone success.
- Cost: many LLM calls (GPT-3.5 plan + GPT-4 decomposer); paper does not headline cost.
- Transfer: tiny action vocabulary + hand-written executors = our skill layer; memory of "reference plans" per goal; recipe/wiki knowledge as structured input (ours = minecraft-data).

## 4. Odyssey / JARVIS-1 / DEPS / Plan4MC / Optimus-1 / MineDojo / BASALT
- Odyssey (IJCAI 2025) https://github.com/zju-vipa/odyssey https://arxiv.org/abs/2407.15325: mineflayer-based; planner/actor/critic LLM trio; skill library 40 primitive + 183 compositional skills (ship hand-written, not learned); fine-tuned LLaMA-3 8B/70B ("MineMA") on 390k+ Minecraft-wiki Q&A for domain knowledge; embedding retrieval (MiniLM) of skills; benchmark = long-term planning (combat multi-mob), dynamic-immediate planning (farming: shear sheep, milk), autonomous exploration. Transfer: large pre-written compositional skill library beats learned library for reliability; wiki knowledge matters for small models (we can inject recipe/fact tables instead of fine-tuning).
- JARVIS-1 https://arxiv.org/abs/2311.05997: multimodal LLM planner + goal-conditioned controllers (STEVE-1-like, visual, NOT mineflayer) + multimodal memory of past successful plans keyed by situation; 200+ tasks, ObtainDiamondPickaxe 12.5% (~5x prior). Transfer: retrieval of prior successful plans by (goal, situation) = our "reference plan" memory.
- DEPS https://arxiv.org/abs/2302.01560: Describe (what happened) -> Explain (LLM self-explains the failure) -> Plan -> Select (a learned goal-selector ranks parallel sub-goals by estimated steps-to-completion). First agent for 70+ tasks, ~2x prior success. Transfer: structured failure description + explanation before replan; choose among candidate sub-goals by *distance/cost* heuristic (deterministic in our case).
- Plan4MC https://arxiv.org/abs/2303.16563: LLM-built SKILL GRAPH (item nodes, edges = quantity relations) generated once offline, then DFS/graph search for skill sequences at run time; skills = Finding / Manipulation / Crafting; 40 tasks, many >10 skills. Transfer: exactly "dependency-graph planner replaces LLM decomposition" - build from minecraft-data recipes, no LLM.
- Optimus-1 https://arxiv.org/abs/2408.03615 (NeurIPS 2024): hierarchical directed knowledge graph (world knowledge) + abstracted multimodal experience pool; Knowledge-guided Planner + Experience-driven Reflector; 2-6x gains across MLLMs; near-human on many tasks. Transfer: knowledge graph as the planner's source of truth; reflector writes lessons.
- MineDojo (NeurIPS 2022 D&B): 3,000+ open-ended tasks, internet-scale knowledge base, MineCLIP; MineRL ObtainDiamond (https://minerl.readthedocs.io/en/stable/environments/diamond.html) with milestone reward ladder (log, planks, crafting table, wooden pickaxe, cobblestone, stone pickaxe, furnace, iron ore, iron ingot, iron pickaxe, diamond) is the canonical tech-tree ladder. BASALT (NeurIPS 2021/22): 4 fuzzy tasks (FindCave, MakeWaterfall, CreateVillageAnimalPen, BuildVillageHouse) judged by human pairwise comparison - useful only as inspiration for "build a house" style subjective eval.
- None of these are cheap-model-judgment-only systems; GITM/Plan4MC/Odyssey are closest in spirit (structured actions + deterministic executors).

## 5. Recent (2024-2026) projects worth knowing
- Project Sid / PIANO (Altera) https://arxiv.org/abs/2411.00114 : 10-1000+ agents in Minecraft. Key architecture idea = CONCURRENCY + information bottleneck: fast reflex/action modules never block on slow LLM modules (planning, reflection, social); a "cognitive controller" aggregates module outputs into one decision that all output streams (speech, action) follow, to keep coherence. Transfer: our LLM-free reflexes + queued chat while a task runs is the same pattern; avoid blocking chat replies on long skill runs.
- Parallelized Planning-Acting https://arxiv.org/abs/2503.03505 (mineflayer): plan the NEXT step while the current action executes; cuts wall-clock latency. Transfer: speculative next-call / pipeline - issue next tool call while skill runs, or have the skill return a precomputed "likely next step".
- Gated Coordination https://arxiv.org/abs/2604.18975 : only invoke LLM/communication when state change warrants it; fewer tokens/calls/latency at equal success. Transfer: event-gated LLM calls (call model only on failure, ambiguity, new player message, goal completion).
- PillagerBench (CoG 2025) https://arxiv.org/abs/2509.06235 : competitive team-vs-team, one mineflayer process per agent; TactiCrafter learns causal dependencies. Low relevance (PvP).
- MineAnyBuild (2025) (arXiv id unverified; see https://www.researchgate.net/publication/392133307) : spatial-planning benchmark for building from instructions - confirms models are weak at generating build plans from language -> use parametric templates/blueprints.
- MineExplorer (2026) https://arxiv.org/abs/2605.30931 (could not fetch full text - >10MB): open-world exploration benchmark for MLLM agents.
- Optimus-3 https://arxiv.org/abs/2506.10357 (generalist MLLM with task experts) - visual, not mineflayer; shows trend: planner + specialised "task expert" executors.
- Mindcraft remains the most active open mineflayer+LLM codebase (5.8k stars, commits Oct 2026). Its ecosystem (MineCollab, mindcraft-ce forks) is the de-facto reference for mineflayer LLM agents; no strong published tech-tree/diamond benchmark number for it.
- No published mineflayer LLM agent with a strong DIAMOND success rate comparable to GITM (67.5%, non-mineflayer simulator w/ hand-written interface) - Voyager (1/3 diamond tool, 102 iterations) is still the main mineflayer data point. A reliably-measured "iron kit / diamond pickaxe with N model turns" result would be novel.

## 7. SYNTHESIS

### 7.1 Cross-cutting findings
- Every high performer (GITM 67.5% diamond, Plan4MC, Odyssey, Optimus-1, DEPS) has the same shape: small structured action vocabulary + hand-written executors + a knowledge-driven decomposition of goals into item dependency trees. LLM is used for plan choice/repair, not low-level control. v1 already matches this; the gap is the DECOMPOSER and VERIFIER being LLM work instead of middleware.
- Voyager's ablation: self-verification (-73% items) and curriculum (-93%) matter more than anything else; skill library compounds later. But Voyager's code-gen loop costs up to 5 GPT-4 calls/task and needed GPT-4-class models (GPT-3.5 = 5.7x worse). A cheap model must NOT write code per task.
- Memory of successful plans (GITM reference plans after 5 successes, JARVIS-1 multimodal memory, Optimus-1 experience pool) is consistently a top-3 contributor.
- Latency/cost tricks from 2025-26 papers: concurrency (PIANO), parallel plan-while-act (2503.03505), event-gated model calls (2604.18975).
- Communication/construction are the weakest areas for every LLM (MineCollab: best model 0.36 construction, <40% blocks right) -> build must be blueprint-driven.

### 7.2 Ranked top-10 ideas for v2
Impact = competence/efficiency gain; Size = rough implementation effort (S <1 day, M 1-3 days, L ~1 week).
1. **Recipe-derived goal planner ("tech-tree compiler") in middleware.** Build a dependency graph from minecraft-data recipes + small hand tables (smelt, fuel, tool-tier mining requirements from blocks.harvestTools, drops, "raw_X from ore Y"). Input: target item+count (+current inventory/known POIs). Output: ordered step list (gather logs -> planks -> table -> pickaxe ... -> smelt ... ) with quantities, deduped against inventory. LLM issues ONE call `achieve({item,count})` (or approves a plan) instead of 15 turns. Mirrors Plan4MC skill graph / GITM decomposer / Optimus-1 knowledge graph. Impact: very high (turns for "full iron kit" from ~30+ to ~2-5). Size: M-L. Eval via crafting-util is an option but we need smelt/mine nodes so own it (mineflayer-crafting-util 0.5.0 `planCraft` can be a reference/check).
2. **Executor with per-step postcondition verification + structured failure reports.** Each plan step has a machine-checkable postcondition (inventory has X, block placed, position within r, health/food ok) - Voyager's #1 ablation (self-verification) done deterministically and for free. On failure return a typed reason {missing:[...], blocked_by, unreachable, danger} (DEPS "describe") so the LLM only decides recovery. Size: M. Impact: very high.
3. **Autonomous-run mode: one LLM call per goal, event-gated re-entry.** Plan executes without the model; model is re-invoked only on: plan done, unrecoverable failure after N deterministic retries, new player message, new hazard class (gated coordination / PIANO concurrency). Add speculative pipelining where cheap (next step prefetch). Impact: very high on tokens/latency (target: <=5 turns per multi-step goal). Size: M.
4. **Deterministic recovery ladder before escalating** (retry w/ different standing spot -> alt tool path -> re-path with dig allowed to an owned/natural block -> relocate search -> escalate). Mindcraft `unstuck` + `self_preservation` modes and our repeat-failure guard are the precedent; extend to named "stuck" classes (stairs/dripstone/water-exit per pathfinder issues). Impact: high. Size: M.
5. **Plan/experience memory (reference plans) on disk.** Store per (goal-type, biome/context) the successful step sequences + durations + failure notes; inject only the top-1 as a hint (GITM: summarise after 5 successes; JARVIS-1/Optimus-1 retrieval). Also store learned-world facts (best mining depth locations, "iron found at X"). Fits "disk is source of truth". Impact: medium-high over time, esp. for repeat tasks (house, farm). Size: S-M.
6. **Parametric blueprint library + deterministic builder for "build a house/farm/portal".** LLM picks template + size + material palette + site (judgment); a placement planner orders layers bottom-up, handles scaffolding, material gather-list (feeds idea 1), clears site non-destructively, avoids player builds (structure-guard). Use prismarine-schematic for .schem import (or mineflayer-schem as reference); NOT LLM block-by-block (MineCollab construction <40%). Include templates: 5x5 wood house w/ door+bed+torches, wheat farm 9x9 w/ water, Nether portal (obsidian frame via water-on-lava-source casting + diamond pickaxe, or ruined-portal repair; light with flint & steel). Impact: high for build tasks. Size: L.
7. **Fix the foundation: pathfinder from GitHub master + createHuman for travel legs.** npm 2.4.5 is 3 years stale; master (Sep-Oct 2026) has real fixes (A* heap bug, diagonal corner cuts, water planning, goto rejecting unreachable goals, door/gate node handling). Pin a commit, run our nav tests, keep our navigate() wrapper. Use createHuman only for pure walking legs (no dig/place) for player-like movement. Impact: medium-high reliability; Size: S (+regression time). Risk: unreleased code; pin and test.
8. **Compact "world model" queries: state-on-demand + LLM-free reflex layer extension.** Keep ground-truth block small; add cheap query tools (Mindcraft style !nearbyBlocks/!inventory) only when needed; port Mindcraft modes missing from v1 (torch_placing underground, item_collecting, elbow_room, cowardice/flee thresholds, night-shelter reflex, auto-bridge lava/water avoidance). Impact: medium (survive-the-night, fewer deaths); Size: S-M each.
9. **Safety/hallucination guards at the tool boundary.** Reject non-existent item/block names with did-you-mean (already) and with recipe feasibility ("copper_sword" never exists; cobblestone is not fuel - Voyager's own hallucinations); validate quantities; recipe tool returns exact needs. Voyager and MineCollab both report hallucinated items/functions. Impact: medium; Size: S.
10. **Eval harness = tech-tree ladder + scripted scenario tasks** (see 7.3) run from JSON task files (Mindcraft format: goal, starting inventory, target, timeout) with telemetry (turns, tokens, wall-clock, deaths). Without it none of the above is measurable. Impact: enabling; Size: M. (Creative-mode `getItems`/ /give / /tp / /time set make setup cheap on our own server.)
Honorable mentions: wiki/fact table injection (Odyssey fine-tuned on wiki; for us a static JSON of mining depths, ore Y ranges, mob drops, light levels - S); Voyager-style curriculum for idle/autonomous mode (LLM proposes next goal from a fixed ladder filtered by deterministic "what's missing" - M); pipelined plan-while-act (S-M); dashboard "plan progress" panel.

### 7.3 Benchmark design lessons (so our eval is comparable)
- Canonical tech-tree ladder (Voyager Table 1; MineRL ObtainDiamond): log -> planks -> stick -> crafting table -> wooden pickaxe -> cobblestone -> stone pickaxe -> furnace -> iron ore -> iron ingot -> iron pickaxe -> diamond (-> diamond pickaxe). MineRL milestone rewards 1,2,4,4,8,16,32,32,64,128,256,1024 (from memory; double-check before citing). Voyager reports "iterations (LLM prompt rounds) to first unlock of wooden/stone/iron/diamond TOOL", mean±sd over 3 seeds/runs, with fail counts (e.g. 6±2 / 11±2 / 21±7 / 102 (1 of 3)). Also: unique items discovered over fixed iterations (63), distance travelled, and zero-shot tasks in a fresh world (diamond pickaxe, golden sword, lava bucket, compass: 18-21 iterations).
- Our comparable metric: report BOTH model turns and wall-clock/minutes-in-game + tokens for each ladder rung from a fresh survival world; N>=5 seeds; success = rung achieved within a budget (e.g. 50 turns / 20 min). Voyager's "iteration" = one LLM program attempt, so our "turns" is roughly comparable; also report tool-calls per turn.
- GITM-style: success rate over N episodes of ObtainDiamond (prior 20%, GITM 67.5%), plus coverage across all 262 tech-tree items (GITM completed all; prior methods ~30%).
- JARVIS-1: tasks grouped by horizon/category (Wood, Stone, Iron, Diamond, Redstone, Armor...) with 30+ tasks/group, success rate per group; ObtainDiamondPickaxe 12.5%.
- MineCollab / Mindcraft task JSON: goal + initial inventory + target items + timeout; binary success for craft/cook; edit-distance to blueprint for construction. Crafting 0.47 / cooking 0.64 / construction 0.36 (Sonnet 3.5) - gives us a reference for "build" scoring: fraction of blueprint blocks correct.
- BASALT-style human pairwise judging for subjective tasks (house looks like a house). We can approximate with checklist rubric (walls closed, door, roof, light, bed, no grief).
- Add efficiency & behaviour metrics the literature omits but we care about: model turns/tokens per success, deaths per hour, stuck events/h, % of tasks needing LLM replan, player-likeness checks (doors used, no pillar-travel, no griefing), chat quality.
- Fix seeds & world state (same LEVEL_SEED, same spawn) so variance is attributable; use /gamerule, /time set day, /difficulty to isolate (e.g. peaceful for tech-tree timing, normal for survive-night).
- Suggested v2 ladder suite (extends standard): L0 wood tools; L1 stone + furnace; L2 full iron kit (pickaxe, sword, helmet, chestplate, leggings, boots, shield, bucket); L3 diamond pickaxe; L4 shelter/survive-night; L5 house from blueprint; L6 wheat farm (harvest+replant, bread); L7 Nether portal (+enter); each with turn/token/time budgets.

### 7.4 Pitfalls others reported
- Code-gen brittleness (Voyager): hallucinated items/functions ("copper sword", cobblestone as fuel), stuck after 4 retries, verifier misjudging success (spider string). Needed GPT-4; GPT-3.5 5.7x worse. Mindcraft ships coding mode off by default for injection-security reasons. => keep fixed skills, validate names.
- Cost: Voyager ~5 expensive calls per task; loops without a token budget blow up. => hard turn caps (we have 50), plan-level not step-level model calls.
- Pathfinding: stuck loops on stairs, dripstone, 2-block gaps, water exit, doors/gates (canOpenDoors "unreliable"), `goto` resolving when no path (fixed on master Sep 2026), GoalFollow broken >1.21.8, hitbox collision bug on 1.21.x, long paths (1000+ blocks) slow. => stuck detection with escalation (we have), prefer waypoint hops <=~100 blocks, test on master pathfinder.
- Undoing own work / place-destroy loops (MineCollab) - idempotent build steps and a build ledger.
- Multi-agent comms scale badly (90% -> <30% from 2 to 5 agents); detailed plan communication costs 15% -> keep multi-bot out of v2 scope or use gated, short messages.
- Resource availability assumptions: planners fail when ore/tree not nearby; need explore-until + remember POIs (GITM `explore` action; Voyager exploreUntil).
- Memory growth: Voyager's retrieval gets noisy with big libraries; keep reference plans few, summarised (GITM: compress after 5).
- Subjective tasks (build) are hard to score automatically - invest in rubric early.
- Parallel plan/act: plans can go stale after world mutations (2503.03505) - re-validate preconditions on dequeue.
- Unreleased dependencies: pathfinder master has fixes + `createHuman` but no npm release; mineflayer-collectblock/tool/pvp/armor-manager are stale (2022-2025) - treat as reference code, not hard deps.
