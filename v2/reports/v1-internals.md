# v1 internals map (design prep for v2)

## 0. Headline findings
- **ROOT CAUSE of door/wall digging (and of "pathfinder never digs" being false): `ensureMovements()` never installs v1's Movements config.** `src/skills/pathfinder-config.ts:43` guards with `!bot.pathfinder.movements || bot.pathfinder.movements.bot !== bot`. But mineflayer-pathfinder 2.4.5 pre-creates a default `Movements` at plugin inject (`node_modules/mineflayer-pathfinder/index.js:19` `let stateMovements = new Movements(bot)`) and exposes it via the `movements` getter, so `.bot === bot` is already true -> `buildMovements()` (canDig=false, canOpenDoors=false, door patch, allow1by1towers=false, liquidCost=3) **never runs**. Verified by instantiating the plugin on a stub bot: default movements has `bot===bot`, `canDig:true`, `allow1by1towers:true`, `liquidCost:1`. Only `maxDropDown` (line 48) and `installDoorAssist` take effect. Consequences: A* may dig any diggable block (walls beside the door; the door cell is a solid wall to the planner since `patchMovementsForDoors` is not applied), may place scaffolding/1x1 towers (the "dirt staircases"), swims freely. Fix: track configured instances in a `WeakSet`/flag instead of comparing `.bot`, or call `setMovements(buildMovements(bot))` once at spawn (bot-factory.ts:111). Tool descriptions (`registry.ts` goTo: "it never digs through blocks") and system prompt line 74 claim the opposite, so the LLM is told something false.
- Eval evidence consistent with this: `v2/runs/v1-smoke-20261009-12{38,46}` t2.door_house: no `mineBlock` call anywhere (only `say`/`goTo`; `bot.dig` is called only from `world.ts:884`), yet the same two planks `(279,67..68,-305)` beside the door `(280,67,-305)` were flagged broken in both runs. Run 1238 opened the door (`door` event) *and* still broke them (the second `goTo` to Tester starts at the door with the door cell planned as a wall); run 1246 has no `door` event and a 9.5s nav = walked through the hole. (The exact digger was not observed live; pathfinder with canDig=true is the only code path that can do it without a `mineBlock` call.)
- **mineBlock "success" counts digs, not pickups.** `world.ts:272-286`: `mined += 1` after `mineOneBlock` returns ok; `mineOneBlock` ends with `await pickUpNearby(...)` whose result is **ignored** (`world.ts:415`) and returns `{ok:true}` unconditionally. `pickUpNearby` (`inventory.ts:57`) scans `bot.entities` immediately after `bot.dig` resolves; the item entity packet is typically not there yet -> "no dropped items" -> nothing collected. In the 1238 chop run telemetry: 10 digs reported `mined 10 jungle_log`, nav events ~20 ms each (bot never moved), one pickup-walk, inventory 3/10. No inventory-delta check anywhere. Fix: wait ~250-400 ms (or until a `entitySpawn` item within 2 blocks) then re-scan; verify `bot.inventory.count(dropId)` delta; count that.
- **Pathfinder 2.4.5 `goto` resolves on empty/partial paths and `stop()` latches while idle** (details sec. 4). v1 papers over the first in `navigate()` (`navigation.ts:140-147`); the second hits `stop` skill (`movement.ts:107`), death hook (`event-hooks.ts:259`), watchdog (`harness.ts:108`), all of which call `pathfinder.stop()` possibly while idle -> next `goto` rejects `PathStopped`.
- Fixed prefix per API call is **~17-19k cached tokens**, not the ~9k our own text suggests (sec. 1). Cost is trivial (~$0.001-0.002/task) because of 93-99% cache hits; latency, not cost, is the Haiku bottleneck.
- Import-cycle wart: `skills/registry.ts` -> `harness.ts` -> `orchestrator/chat-router` -> ... -> `agent/skill-tools.ts` -> `registry.ts`. Importing `registry` or `skill-tools` first throws `Cannot access 'SKILL_SPECS' before initialization`; importing `agent/npc-agent.ts` first works. Matters for any v2 module (planner/tests) that imports the registry directly.

## 1. Agent loop
**Flow (per_task default, `config/bots.yml` session_mode):** mineflayer `chat`/`whisper` (`event-hooks.ts:114/121`) -> `maybePreempt` stop side-channel (`event-hooks.ts:320-340`; only if a CANCELLABLE skill in flight, strict `isStopCommand`, sender == conversation partner) -> `chat-router` -> `NpcAgent.pushChat` (`npc-agent.ts:75`): drops while rate-limited (:76), `recordConversation` to disk (:83), `maybeInterrupt` (:99: if backend busy + stop command -> `runSkill stop` + `interruptCurrentEvent`), `formatUserMessage` (:148; header + routing note) -> `ClaudeBackend.pushUserMessage` (`claude-backend.ts:751`) -> `pending[]` -> `maybeStartTask` (:783): `waitForToolIdle` (:841; up to 35s, re-asserts cancellation every 200ms) -> splice+coalesce all pending ("N messages came in while busy, latest intent wins") -> `worldContext()` (:858; `buildAgentContext`, 2s timeout, null on failure) -> `openSession()` (:337; **a fresh SDK `query()` per task**, new MCP server per session) -> push one user message `"{context}\n\n{chat+note}"`.
- Loop is observability only (`runSession` :375, `handleMessage` :448); tools execute inside the SDK's in-process MCP server (`adapters.ts:24-37` -> `skill-tools.ts wrapSpec` -> `spec.run` -> `runSkill`). Session closed when `result` arrives (:523 ff.; `query.close()`), `onSessionEnded` (:399) starts next queued task.
- **SDK options** (`claude-backend.ts:344-362`): `model: claude-haiku-5-5` (`behavior.ts:20`), `thinking: {type:"adaptive"}`, `effort: "medium"` (const `HAIKU_EFFORT` :102; Haiku-only), `systemPrompt: buildSystemPrompt(username)` (plain string -> replaces CC preset), `mcpServers: {minecraft-skills}`, `tools: []` (built-ins off), `allowedTools` = 37 `mcp__minecraft-skills__*`, `permissionMode: bypassPermissions`, `persistSession: false`, `maxTurns: 50` (`limits.ts:12`). No `fallbackModel`, no `maxBudgetUsd`, no hooks/`canUseTool`, no `settingSources`.
- **Turn counting:** one count per API message id (:453-459; thinking/text/tool_use blocks of one message share an id). Warn at 80% (:477). On `error_max_turns` a follow-up note is queued (`queueMaxTurnsFollowUp` :610) asking Haiku to report status. Refusals (`stop_reason==="refusal"` :492) whisper the partner.
- **Tokens/telemetry:** only at the terminal `result` message: `usageOf(msg)` (:1074; cumulative per-query `usage` + `total_cost_usd`) -> `finishEvent` (:426) -> `endTelemetryTask` (:927) emits `task_end {turns, durationMs, firstReplyMs, toolCalls, toolFailures, inputTokens, outputTokens, cacheRead/CreateTokens, costUsd, outcome, subtype}`; `task_start` (:904) has `contextChars`, `contextBuildMs`, `queueWaitMs`, `coalesced`. **No per-turn token or per-turn latency events**; thinking text is logged truncated to 240 chars (:464) but not persisted. `sessionUsage` accumulates only on `success` results (:542) - failed/max-turn tasks' tokens are not in the dashboard total (telemetry still has them). Other event kinds: `skill` (harness), `nav`, `door`, `pillar`, `structure_skip`, `guard_refusal`, `reflex`, `rate_limit`, `death`, `hurt`, `chat_in/out`, `connection`, `loop_lag` (`observability/telemetry-types.ts`).
- **Context block** (`planning-context.ts:47 buildAgentContext` -> `worldLines` :74), always in the *user* message so the cached prefix stays byte-stable: game mode, position/dimension/facing, health/food/time/weather, held, full inventory summary, top-8 nearby block groups (radius 16, `observeSurroundings`), <=6 entities, dropped items, <=5 known storage (top-4 contents each), <=5 utilities, <=5 waypoints, last death, last 8 action-log entries w/ ages (120 chars each), current/remaining task queue, then "# Recent conversation" from `conversation.json`. Measured `contextChars`: 529-649 in the empty eval world; expect ~1-2k chars (300-500 tokens) in a populated world. The model is told it is ground truth.
- **System prompt** (`system-prompt.ts:16`): **10,071 chars (~2.5k tokens)**; 6 numbered rules, then Chat/Deciding/Getting things done (hard-coded recipes + tool tiers: wood/stone/iron/diamond - **no copper tools**, though 1.21.9 has them)/Gathering/Moving/Building/Creative/Batch/IDs/Using items/Safety. Hybrid/local prompts (:134-216) are dead weight for v2 (backends `hybrid-backend.ts`, `local-backend.ts`, spikes).
- **Tools** (37 in `SKILL_SPECS`, `registry.ts:126`; 36 + getItems): total description 10,547 chars, total JSON-schema 12,359 chars. Largest descriptions: craftMany 564, goTo 547, craft 504, placeBlocks 499, getItems 486, mineBlock 458, smelt 457, mineBlocks 423, observeSurroundings 409, withdrawManyFromChest 369, pillarUp 340. Largest schemas: goTo 680, mineBlocks 694, smelt 624, equipLoadout 604, craftMany 541. Estimated text-only prefix ~8.5-10k tokens; **measured** `inputTokens+cacheRead+cacheCreate` per 3-5 turn task = ~70-95k => ~17-19k per API call (the ~8k remainder is SDK-side overhead/JSON tool wrapping; not inspected). - **Repeat-failure guard** (`skill-tools.ts:44-169`): per bot, per event; key = `name:stableKey(args)` (sorted JSON). After `MAX_IDENTICAL_FAILURES=2` identical failing calls it refuses without executing (:159-165, emits `guard_refusal`); after 6 total failures every failure message gets a "stop and tell the player" suffix (`FAILURE_NUDGE_THRESHOLD`). Weakness: keyed on args only, not world state (a moved bot / new inventory still gets refused), and `ok:true` partials clear it. Guard lives only on the Claude surface - a v2 deterministic executor needs its own typed-failure/retry layer.
- Also: `say/whisper` wrapper arms follow-up routing + conversation log (:133-155). Rate limit: `RateLimitCooldown` (`behavior.ts:36`) drops chats while active; no retry.
