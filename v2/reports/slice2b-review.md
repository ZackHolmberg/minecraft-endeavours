# Slice 2b review (commit ff27f8d)

Read-only review: nothing run. Unit tests and live behaviour were not re-verified; findings come from reading the code.
Ranked by severity, with file:line (v2 worktree), failure scenario and fix.

## HIGH

**H1. Underground explore: the dig-timeout timer is never cleared, so it aborts later digs.** `src/jobs/explore.ts:351-361` `digCell` does `Promise.race([bot.dig(b), new Promise(... setTimeout(() => { bot.stopDigging(); rej() }, 15000))])`. The timer is never cleared. Every *successful* dig leaves a timer that, 15 s later, calls `bot.stopDigging()` and rejects into a settled race. The staircase and branch tunnel dig a cell every 1-3 s, so from about 15 s in, roughly every third timer lands in the middle of a live dig. `bot.dig` rejects with "Digging aborted", `digCell` returns "failed", and `advance` returns `{ok:false}`. Result: "staircase blocked ... dig failed", or "branch mine blocked" after one turnaround. Underground explore dies within about 20-40 s. This path was only unit-tested, never run live (slice2b.md says so). Fix: keep the timer handle, `clearTimeout` it in a `finally`, and call `stopDigging` only if the race really timed out.

**H2. Unbounded `[job failed]` -> Haiku -> `achieve` loop; there is no cap or backoff.** `src/jobs/tools.ts:38-66`, `src/jobs/describe.ts:70`, `src/agent/skill-tools.ts:64-80` The only protection is prose ("Don't just call achieve again"). A new `achieve` returns `ok:true` ("job started"), so the repeat-failure guard (which only counts `ok:false` results) never fires. Scenario: "get diamond_pickaxe" in a world with no diamonds nearby. Each cycle runs the ladder: widen 64/96/160, then 2 explores of up to 6-10 min each, then fail.; The failure event starts a fresh Haiku task (~120k input tokens), which calls `achieve` again.; Nothing stops this overnight, and it burns subscription quota.; Fix: persist a failure ledger (goal signature, kind, time) in the runner or `job.json`. `achieve` refuses with `ok:false` ("failed N times: <kind>; ask the player") when the same goals have failed 2 times within about 15 min, with no new player chat since.; Clear the ledger on a player message that routes to the bot.; Add a minimum gap before re-planning identical `no_source` goals.;

## MEDIUM

**M1. Reconnect and shutdown run failing steps on a dead bot, then wake Haiku.** `src/jobs/wire.ts:43-82`, `src/index.ts:74-75` Nothing listens for `bot.on("end")`. The old runner is disposed only when the new connection's `attachJobRunner` runs, after the reconnect delay. Until then, steps run against the disconnected bot and fail "internal" -> retry -> replan x5 -> `finish("failed")`. That calls `onEnd` -> `pushJobEvent` to the stale agent: a wasted Haiku task, `job_end=failed` instead of `interrupted`, and the player is told a false failure. Shutdown has the same problem. `s.stop()` (disconnect) runs *before* `unregisterJobRunner`, so the job can end as `failed` and queue a Haiku task during teardown. Fix: `bot.once("end", () => runner.dispose())` in `attachJobRunner`.; Dispose runners before stopping supervisors (`index.ts:74`).; Make `dispose()` set `disposed` before awaiting, and have `finish()` skip `onEnd` when `disposed` is set.; Consider a `[job interrupted]` note to the new agent so the requester is told.;

**M2. The `runSkill` 10-min watchdog silently cancels long gather/smelt steps.** `src/jobs/runner.ts:72-85`, `src/skills/harness.ts:40,104-108`, `src/jobs/steps/gather.ts:11`, `src/jobs/steps/smelt.ts:9` gather's step timeout is `4 min + 20 s * count`, capped at 15 min. It exceeds 10 min for count >= 19. One `mineBlocks` call can carry maxCount up to 128, and `smelt` chunks go up to 64 (640 s). The watchdog calls `cancellation.request()`. That reaches `notifyStop` with `internalStop == 0`, so the job is treated as a player stop and ends `cancelled` with no event. Haiku is never told, and the player gets nothing. Fix: cap each skill call below the watchdog (e.g. gather `maxCount` <= 24 per call and smelt chunk <= 32, since the outer loop already repeats). Clamp `stepTimeoutMs` to about 9 min. Alternatively let `runSkill` skip `request()` listeners for its own watchdog.

**M3. Stop and death windows are lost or silent.** `achieve` during start: `startInner` is `isRunning()` false for the buildView + plan window (~1 s). `notifyStop` and `maybeInterrupt` (`npc-agent.ts:99-110`) both see no job, and `interruptCurrentEvent` closes only the session, not the in-flight tool call. A "stop" in that window is acknowledged, then the job starts. Fix: bump a `stopEpoch` in `notifyStop`/`cancel` and have `startInner` abort if it changed since entry. Death: `event-hooks.ts:262` calls `request()`, the job ends `cancelled`, and no event is sent. The player's request silently dies with the bot, and the context block mentions it for only 2 minutes. Fix: send a `[job interrupted: died]` event so Haiku can say so or offer to retry. This also covers the M2 watchdog case.

**M4. Stale step and reflex interference: job steps share the single flag and `currentTool` slot with Haiku's exempt tools.** `src/skills/harness.ts:86-92`, `src/jobs/runner.ts:180-192`, `src/skills/auto-behaviors.ts:75` Exempt tools (`say`, `observeSurroundings`, `checkInventory`) still go through `runSkill`. `begin()` clears the stop flag. If a step's skill has not yet polled the flag set by the step timeout or `cancel()`, the stop is lost.; `cancel()` then waits the full 35 s. If that times out, `startInner` or the auto-cancelled tool proceeds while the old step keeps driving the bot. The new skill's own `begin()` clears the flag, so the old step is never told to stop.; `currentTool.begin("say")` overwrites the step's entry. The step's `end(oldToken)` is then a no-op, and `say`'s end sets it to `null` while the step is still running.; `explore()` is not run via `runSkill` at all (`explore.ts:148`; runner.ts:358), so `currentTool` stays null for up to 10 min. `auto-behaviors.isBusy` keys off `currentTool`, so look-at-player, auto-armor window clicks and auto-eat equips run mid-dig. These reflexes can also open windows against the dig or craft. Fix: Hold one job-level `currentTool.begin("job")` for the whole job.; Run exempt read-only tools without `begin()`/`currentTool` (a `passive` option on `runSkill`).; Wrap `explore` in `runSkill`.; Make `cancel()` hard-fail (`ctrl.abort()` plus a repeated `requestStop` poll) until the loop ends.;

**M5. Surface explore never returns, so the bot ends up very far from where it started.** `src/jobs/explore.ts:187-206`, `src/jobs/recovery.ts:80-84` Legs 40, 40, 80, 80, 120, 120 (six legs, 480 blocks of path) are walked with no return. `MAX_EXPLORES = 2` means a failing job can end ~500-1000 blocks from the base, the tables and the player, in unloaded terrain. The failure event doesn't say where the bot is. A later "retry" job plans against that remote area (wrong stations, stranded chests). Fix: record the origin before exploring and walk back (or `goTo` the origin) on `found:false`. Put the end position in the failure detail.

**M6. World-view builds block the event loop; the cost grows steeply with radius.** `src/jobs/world-view.ts:84-92` About 50 synchronous `bot.findBlocks` calls (0.7-1.4 s at r=48 per the report) run back to back with no yield. Replans and verify use `scanRadius`, which becomes 96/160 after widening. This is my estimate, not measured: on the order of 10x more loaded columns at r=160, i.e. several seconds to 10+ s with no keepalive, pathfinder or reflex ticks, enough to risk a keepalive timeout. Fix: `await new Promise(setImmediate)` every few types.; Scan only the goal's blocks at wide radii.; Cap the view radius at 96.;

**M7. Job-end event coalescing: "latest intent wins".** `src/agent/backend/claude-backend.ts:823` If a player chat and a `[job finished]` or `[job failed]` event are queued together while a task runs, they are merged under "handle them together, latest intent wins". When the job event is the later entry, Haiku can treat the notification as the player's latest wish and drop the chat request, or answer only the job. Fix: label synthetic events (`(system notice, not a request)`), and in the batch builder put notices first.

## LOW

## Verified fine
- The exempt list (`say`, `whisper`, `observeSurroundings`, `checkInventory`, `remember`, `setTaskQueue`, `advanceTaskQueue`, `achieve`, `cancelJob`) covers all read-only tools in the registry. `goTo`, `mineBlocks`, `stop` and the rest correctly cancel. `stop` skips the prefix text.
- `achieve` while a job runs: `start()` is serialized through `chain`. The old job is `finish("cancelled")`-ed (idempotent), the controller aborted, and its loop awaited (<= 35 s) before the new view is built. A stale loop can't mutate the new job (`live()`, `setProgress` and `finish` are guarded by `job.status`).
- The job-end event is delivered at most once: `finish` is idempotent, only done/failed call `onEnd`, and cancelled/interrupted jobs queue none.
- `notifyStop` vs `internalStop` is correct, since `request()` runs its listeners synchronously inside `stopInternal`. The listener is unsubscribed via `onDispose`.
- `job.json` is written with `saveJsonAtomic` (tmp + rename, sync). A leftover `running` job becomes `interrupted` at boot, with `job_end` recorded.
- The recovery ladder is bounded: 1 retry per episode, <= 5 replans per job, <= 2 explores per step key, a 30-min job cap, and a bounded explore time (6 min surface, 10 min underground, 140 cells).
- Explore digging safety is sound apart from H1: it checks all 6 neighbours of every cell for liquid, a solid non-magma floor (no pits), the structure guard and a natural-diggable whitelist. The staircase drops 1 block at a time, never straight down, and has a gravel re-dig loop.
- Executors: baseline captured once per episode; `settleCount` handles the stale inventory; craft, withdraw and smelt use `>= target`, so over-crafting is harmless; `classifyFailure` is ordered sensibly. Table/furnace search radii match (32) between the planner view and the craft/smelt skills.
- Furnace fuel check: `furnace.fuel > 0` handles a lit last coal. NaN/undefined fall back to the old path, so the change is safe.
- Eval: `jobState` reads a per-scenario telemetry dir (`runner.ts:168`) and a cancelled job still emits `job_end`, so there is no orphan-hang across scenarios. The job + follow-up pattern doesn't end early in the normal case.
- The context block job section is small (about 3-5 lines, a one-liner after the job ends, shown for 2 min).
