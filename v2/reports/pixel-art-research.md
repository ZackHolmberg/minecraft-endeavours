# Pixel art: image -> blocks research (2026-10-11)

Verdict up front: **no maintained, license-clean, programmatic JS/TS image->block library exists.** Every real tool is a GUI/web app or GPL. Build a thin pipeline ourselves (`sharp` + CIELAB nearest + a small bundled palette) and feed our existing blueprint builder. It is about 150 lines of pure code, and I prototyped the core (below).

## 2. Own pipeline: building blocks

- **Decode/resize: `sharp` 0.35.5 (Apache-2.0, published 2026-09)**, fast, prebuilt binaries for darwin-arm64/linux. Relevant knobs ([constructor](https://sharp.pixelplumbing.com/api-constructor/), [resize](https://sharp.pixelplumbing.com/api-resize/)): `limitInputPixels` (default 268M, set ~25M), `failOn: "error"`, `animated: false`, kernels incl. `nearest`/`lanczos3`, `.flatten({background})` for transparency, `.raw()` for RGBA. Alternative `jimp` 1.6.1 (MIT, pure JS, slower, no SVG). `pngjs` is already in node_modules (5.0.0, transitive via qrcode) but is PNG-only, no resize. Prefer sharp; it adds a native dep (check the box builds on the deploy host: unverified on the Docker/launchd target).
- **Color matching: write ~20 lines of sRGB->CIELAB + squared distance (ΔE76) ourselves.** Libraries exist ([`culori`](https://www.npmjs.com/package/culori) MIT 4.0.2 has deltaE2000; `color-diff` BSD-3; `image-q` MIT but last release 2022) but with a palette of 16-48 entries a hand-rolled loop is 2 ms for 759 px and has no dependency. Use `culori` only if we want CIEDE2000/OKLab.
- **Dithering:** Floyd-Steinberg (error diffusion in linear/Lab) is ~25 lines. Default **off** for logos (flat art), **on** only for photos.
- **Block color table.** Nothing in `minecraft-data` (blocks have no color fields; checked `white_concrete` on 1.21.9). Generate it: [`PrismarineJS/minecraft-assets`](https://github.com/PrismarineJS/minecraft-assets) has `data/1.21.9/blocks/*.png` (repo has **no license file**; textures are Mojang's). Average each texture at dev time with a script and commit **only the numeric JSON** (`{block, rgb}`), plus a validity test that every name exists in `minecraft-data` for the configured `MC_VERSION`. Derived colour numbers are facts, not the textures, but flag the provenance in the file header. I fetched 49 textures (16 colors x concrete/wool/terracotta + plain terracotta) and averaged them: white_concrete 207,213,214; red_concrete 142,33,33; blue_concrete 45,47,143; red_wool 161,39,35. (Do not bundle mapartcraft's tables: GPL-3.0 and they are map colors.)
- **Palette families to ship:** `concrete` (default; flat, 16 colors, no texture noise), `wool`, `terracotta` (muted, 17), `mixed`, plus an explicit `blocks: string[]` allowlist. Optional later: `gold_block`/`quartz`/`stone` extras for greys and gold. Keep glazed terracotta and anything with facing/pattern out (orientation-dependent).

**Prototype (verified, scratchpad only):** Canadiens SVG-thumb PNG (500x342) -> `sharp` resize 33 wide (33x23 = 759 blocks) -> Lab nearest. Results:
- Wool+concrete together produced spurious pink_wool/light_gray_wool and duplicated white/red in two block types. **Use one family** (default concrete).
- Even concrete-only, anti-aliased edges leave light_blue/pink/blue halo blocks at low resolution. Mitigation to ship: **cap the palette** (median-cut / k-means to K=4-6 dominant colors of the resized image, then map each to its nearest block), and resize with area-average (`lanczos3`) then quantize, not the other way. Halos vanish when edge colors collapse into the dominant ones.
- 2.2 ms for the match; decode+resize dominates (<50 ms).

**Fetch hardening (for a/b; owner is security-conscious).** Based on the [OWASP SSRF sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html):
- https only; **host allowlist by default** (`upload.wikimedia.org`, `commons.wikimedia.org`, `en.wikipedia.org`, `i.imgur.com`, `cdn.discordapp.com`...), configurable. Arbitrary-host mode is a separate off-by-default switch for the owner.
- Resolve DNS ourselves, reject any A/AAAA in loopback, RFC1918, link-local (169.254/16 incl. metadata), CGNAT 100.64/10, ULA fc00::/7, multicast, `::ffff:`-mapped v4, then **connect to the validated IP** (undici `Agent({ connect: { lookup } })` with the check inside `lookup`, defeats DNS rebinding). Reject IP-literal hosts and non-443 ports.
- Redirects: manual, max 3, re-validate every hop (host allowlist + IP check). No credentials/cookies sent.
- Timeouts: 5 s connect, 10 s total (`AbortSignal.timeout`). Stream with a **byte cap** (e.g. 5 MB; abort mid-stream, don't trust Content-Length). Content-Type must be image/png|jpeg|webp|gif; then **sniff magic bytes** and ignore the header. Refuse SVG from non-Wikimedia hosts (billion-laughs/external refs; sharp's SVG handling not audited here -> unverified); for Wikimedia take the raster thumb instead.
- Decompression bombs: read dimensions with `sharp(buf).metadata()` first, reject >25 MP; `limitInputPixels` on the real decode; `animated:false`; run decode in a `worker_threads`/child process with a memory limit so a native crash can't take down the bot (see §4).
- Per-player rate limit (e.g. 3 fetches/10 min), global concurrency 1, log URL + host + bytes to telemetry. Never fetch a URL that came from a *tool result* of another fetch, only player/chat-supplied or API-derived Wikimedia ones.

## 4. Recommendation

**Adopt: sharp + bundled Lab palette + our blueprint builder.** Integrated tools lose on license (GPL), model (map art), and scriptability; the pipeline is small, deterministic, unit-testable and keeps Haiku out of coordinates.

**Tool shape (one registry entry beside `build`):** `pixelArt({ source: {url} | {name} | {file}, width?, scale?, palette?, orientation?, at?, dither?, maxColors? })`, which starts a background job exactly like `build`.
- `width` = blocks wide (default 32, clamp 8..128). `scale` int 1..4 multiplies it ("triple size" -> `scale:3`, so 96 wide, aspect preserved; height = round(W * h/w)). The tool echoes the final WxH and block count; hard cap ~6000 placements / 96 high (scaffold height), over cap -> clear error telling Haiku to lower width. The ambiguity "triple of what" is Haiku's judgment (it picks a base width), the arithmetic is code.
- `palette`: `concrete` (default) | `wool` | `terracotta` | `mixed` | `{blocks:[...]}`. `maxColors` default 6 for logos. `dither` default `false`.
- `orientation`: `wall` (default, vertical plane facing the player, image top = highest y, columns mirrored per facing so it reads correctly from the viewer side; verify against `orientCell`) | `flat` (row 0 = far edge, placed at `y = -1` replacing the ground so it is walkable art; the builder's `y = 0 / -1` convention means flat needs a ground-level layer, which is a builder change to confirm). `at`: `'here'` | `{x,y,z}` like `build`. Transparent pixels = **skipped** (no placement), optional `background` block.
- Output: a new `BlueprintKind` `"pixelart"` producing `Blueprint { placements: {x,y,z,block,role:"wall"}[], clear:[], size, margin:1 }`, which the existing job already orders bottom-up, scaffolds, verifies by count, and supplies via `getItems` (creative).
- **Where it runs:** conversion is pure and ms-fast, so the *conversion* (`src/build/pixelart.ts`, pure like the rest of `src/build`) runs in-process. **Fetch + decode run in a child process** (`child_process.fork`, `execArgv --max-old-space-size=256`, 15 s kill timer) that returns the raw RGBA of the resized image only, isolating native image-decoder crashes and bombs from the orchestrator. Palette-cap quantization happens on the resized raw buffer in-process.
- **Materials:** creative -> one `getItems` call per palette block (<=6 blocks, up to W*H/6 each; stacks of 64 and the "inventory fills up" warning in the `getItems` description mean >~30 stacks needs chunked top-ups: the builder already tracks missing). Survival: return the material list up front (`countBlocks`), refuse if the count exceeds a sanity cap, and gather/craft path via existing `achieve` (concrete needs powder+water, so default survival palette to **wool/terracotta/stone-family only**: unverified recipe cost; or just require the player to supply).
- **Provenance/safety:** persist the source URL/title + license string in the job summary; surface "trademarked" note to the player, no extra gating.

**Test plan:** (1) unit: sRGB->Lab sanity (white/black/red nearest), palette JSON validity vs `minecraft-data` for `MC_VERSION`, every name placeable; (2) golden: committed 64x64 PNG fixtures (flat logo, gradient, transparent PNG, 1x1, panorama 4:1) -> expected grid strings, per palette and with/without dither; (3) scale math (`width*scale`, aspect, caps); (4) orientation matrix: 4 facings x wall/flat, assert a 2x2 asymmetric image reads correct from viewer side (mirror bug is the likeliest defect); (5) SSRF suite against a local test server: `127.0.0.1`, `localhost`, `169.254.169.254`, `[::1]`, decimal/octal IP forms, DNS name -> 10.x, redirect to private, redirect loop, slowloris, 50 MB stream, lying Content-Length, `.png` URL serving HTML, decompression-bomb PNG (e.g. 30000x30000 of one color), SVG from non-allowlisted host, animated GIF; (6) a v2 eval scenario: "build a Montreal Canadiens logo, triple size" in the test world, assert job completes, block count matches, no hand-written coordinates in the transcript.

**Estimate:** palette script + JSON + tests ~0.5 d; pure converter (resize contract, Lab, quantize, dither, orientation, blueprint) ~1 d; fetch/SSRF module + child-process isolation + tests ~1 d; registry entry/system-prompt line/job wiring + name lookup (Commons/Wikidata) ~0.5 d; flat-layer builder change + eval scenario + docs ~0.5 d. **Total about 3.5 d**; an MVP (file folder + Wikimedia-only allowlist + wall + concrete) is about 2 d.
